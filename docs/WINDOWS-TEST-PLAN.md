# Windows Test Plan

Personae's Windows code paths are **written from Claude's shipped code + Windows docs but not yet run on a real Windows machine** (the dev host is macOS, so `#[cfg(windows)]` code is not even compiled there). This checklist is the gate before advertising Windows support. Every box is a `TODO(verify)`.

> **First step on a real Windows box: it must COMPILE.** `#[cfg(windows)]` code has never been through `cargo check`/`cargo build` on this repo. Expect to fix compile errors first (imports, `CommandExt`, arg shapes). Build with `cargo build` in `src-tauri`, or the full app with `npm run tauri build` / `cargo tauri build`.

> **Field-confirmed (Windows user, v0.1.0, manual repro — 2026-08):** A Windows user reproduced the multi-account mechanism by hand and confirmed: (1) `CLAUDE_CONFIG_DIR` isolates accounts perfectly; (2) each config dir gets its own `.credentials.json`, `settings.json`, and `history.jsonl`; (3) the OAuth sign-in flow (browser link + code) works in a Windows terminal. This validates the *mechanism* `imp_win` is built on — but it is **not** an end-to-end test of Personae's own launchers/quoting, so every CLI box below still must pass.

> **Session verification (Claude Code, real Windows machine, 2026-08-18):** Ran a genuine (non-GUI) pass — `cargo build`/`cargo test`, plus two temporary `#[ignore]`d probe tests that called the real compiled `cli`/`terminal`/`ide` functions against this machine's actual `%APPDATA%`/`%LOCALAPPDATA%` state (both removed after use, not left in the suite). Boxes below marked ✅ **2026-08-18** are genuinely verified with real evidence from that pass; boxes marked ❌ are explicitly **not** verified and say why — mostly because they require driving the Personae GUI, watching a real console/dialog appear, or completing an interactive OAuth browser flow, none of which this session had tooling for (no click/screen automation). Unmarked boxes are unchanged from before this pass. This machine has: a native `claude.exe` at `~/.local/bin` (no npm shim), VS Code installed (no Cursor/Windsurf/Antigravity), Windows Terminal installed, **no Claude Desktop installed**, and exactly one real signed-in CLI account.

> **Session verification (Claude Code, same machine, 2026-08-19):** Claude Desktop is now installed on this machine (as a Windows Store/MSIX package: `Claude_pzs8sxrjxfjjc`) — the Desktop-profiles section below is no longer blocked on "not installed." Verified live via direct interactive `PowerShell` calls (`Get-AppxPackage`, `Start-Process`) — deliberately **not** as `cargo test`s, even `#[ignore]`d ones: an earlier attempt to script the full `create`/`launch`/`quit`/`delete` lifecycle as an `#[ignore]`d Rust test (with real multi-second sleeps to let the real process actually start/stop) was rejected as too slow for the suite and removed before being run to completion. What genuinely got verified this pass, and what didn't, is spelled out per-box below rather than assumed.

## Environment / tips
- Install the Claude Code CLI (`npm i -g @anthropic-ai/claude-code`, or the native installer). Confirm `where claude` resolves it.
- Override binary resolution for testing with `set CLAUDE_CLI_BIN=C:\path\to\claude.cmd`.
- Per-account config dirs live under `%APPDATA%\Personae\CLI\<slug>`; launchers under `%LOCALAPPDATA%\Personae\CLI\apps` (renamed 2026-08-19 from `ClaudeProfilesCLI`; existing accounts self-migrate on first `list()` after the update — see `cli::migrate_legacy_dirs`). **Verified live 2026-08-19** against this machine's two real signed-in accounts (`justin`, `test`): ran `cli::list()` once via a throwaway `cargo run --example` (no sleeps, single call — not committed), confirmed both accounts still reported `logged_in=true` with the new `config_dir`, then confirmed on disk that the old `ClaudeProfilesCLI` roots (both `%APPDATA%` and `%LOCALAPPDATA%`) were gone, the new `Personae\CLI` roots held the same `.credentials.json`/`launch-history.json`/launcher `.cmd` files, and nothing was left orphaned.

## Desktop profiles (`windows.rs`)
- [x] ✅ **2026-08-19** `claude_found()`/exe-resolution — verified live against a real MSIX/Store install (`Get-AppxPackage *Claude*` → `Claude_pzs8sxrjxfjjc`, `InstallLocation` under `C:\Program Files\WindowsApps\...`). Direct `Start-Process` on the resolved `app\Claude.exe` launched a real, fully-running instance (confirmed PID + process tree, then cleanly stopped). **A real bug was found and fixed in the process**: `CLAUDE_EXE_CACHE` memoized the resolved path for the whole app session with no liveness check; the Store silently auto-updated Claude mid-session (`1.30096.5.0` → `1.32352.1.0`, a new versioned `InstallLocation` folder — MSIX has no unversioned stub the way classic Squirrel installs do), and Personae kept using the now-deleted old path until restart, surfacing as "the system cannot find the file". Fixed by validating the cached path's `is_file()` on every read and transparently re-resolving if it's gone. Also added a user-facing override setting (Desktop panel's new Settings button) for when auto-detection still picks wrong.
- [x] ❌ **2026-08-19** `create`/`launch`/`quit`/`delete(purge)` through Personae's own code paths (write the `.cmd`+`.name`+tinted `.ico`+Start-Menu `.lnk`, launch with an isolated `--user-data-dir`, confirm running via `list()`, quit, confirm stopped, delete and confirm cleanup). **Rejected** — a first attempt scripted this as an `#[ignore]`d Rust test with real sleeps between steps; it was interrupted (too slow for the suite — see the note above) before completing, and was removed rather than left half-run. The `create()` step did leave real throwaway launcher/data-dir files behind, which were confirmed and manually cleaned up (no leftover isolated Claude process was ever spawned — verified via `Get-CimInstance Win32_Process`, no `claude.exe` referenced the throwaway profile's data dir). Redo this as either a fast mocked unit test (mock the process/PowerShell boundary) or a short, deliberate one-off live click-through — not as a multi-second `cargo test`.
- [x] ❌ Two profiles run concurrently, each with its own `--user-data-dir`. **Rejected** — blocked on the box above.
